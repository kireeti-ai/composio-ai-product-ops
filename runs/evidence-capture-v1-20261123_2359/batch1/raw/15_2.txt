Pylon MCP Server The Pylon MCP Server exposes Pylon data to AI tools that support the Model Context Protocol (e.g. Claude, ChatGPT, Cursor). AI tools authenticate with OAuth or an API token and can read and update issues, accounts, contacts, knowledge base articles, tasks and projects, triggers, and more within the authenticated identity's permissions. Server URL (US): https://mcp.usepylon.com Server URL (EU): https://mcp.eu.usepylon.com Auth: OAuth 2.0 or an API token. Actions are performed as the signed-in user or the token's identity, with that identity's current role and permissions. Transport: Streamable HTTP (stateless; no server-side sessions). Setup in Pylon Open Settings > AI Controls > MCP Server in Pylon. Copy your workspace's regional MCP URL from Installation and use it in your AI tool. For client-specific instructions, see connecting to the Pylon MCP Server . Authentication Both methods use the same regional MCP URL. Choose the method your client supports. OAuth Use OAuth with AI tools that offer an interactive connection flow. Add the regional MCP URL to your client, then sign in to Pylon when prompted. MCP requests run as the user who authorizes the connection. API token Use an existing API token for headless workers, scripts, or MCP clients that support custom authorization headers. You don't need a separate MCP token or an interactive sign-in. Create or choose an API token . Configure your client with your workspace's regional MCP URL. Include this header on every MCP request: Replace <API_TOKEN> with the token value. Use https://mcp.usepylon.com for US workspaces and https://mcp.eu.usepylon.com for EU workspaces; the token must belong to the same region. A token with its own identity uses the role assigned to that identity. A token linked to a teammate or bot uses that user's current role and permissions. The identity must have MCP Access , and each tool still requires the permissions for its operation. Any IP allowlist configured on the token also applies to MCP requests. Some clients only support OAuth connections. Use their OAuth flow if they don't let you configure an authorization header. What you can do with MCP today The authenticated user or token identity needs the MCP Access permission to connect. The standard Member and Admin roles include this permission. Each tool also requires the permissions for its operation. Access follows the same scoping as the Pylon dashboard — the MCP cannot return data that the authenticated user cannot already see, or perform writes that the authenticated user cannot already write in the UI. Some tools also require a plan feature, noted in their section. Rate limits apply per tool, elaborated below. Use the tool names below when configuring your AI client. Your client discovers the input schema for each tool through MCP; available tools depend on your workspace, plan, and permissions. For a tool whose input schema includes arguments , put its required and optional fields inside that object. For example: Use the schema returned by your client for the exact fields. Writes apply immediately; confirm the intended change before calling them. If the outcome of a write is unknown, check the record before retrying. Write tools reject arguments they don't recognize instead of ignoring them; the error names the unknown arguments and lists the valid ones. A different casing of a field name, such as customerPortalTitle for customer_portal_title , is accepted, and tools with a state field also accept status . Supply each field only once: sending a field under both its name and an alias returns an error. Issues AI tools can send replies to customers and post internal notes for your team. A reply goes straight to the customer on the issue's channel (Slack, email, chat, etc.) and can't be unsent, so AI tools are instructed to show you the exact message and get your approval before sending it. Most AI tools also ask you to confirm each reply. On large pages, max_messages_per_issue keeps only each issue's latest messages ( messages_truncated is set when older ones were dropped), and max_message_chars cuts each message body to that many characters ( body_truncated is set). Set include_total to also get the exact number of matching issues you can read across all pages; it costs an extra query, so use it when sizing work rather than on every page. If the query is too broad to count exactly (it may match more than 1,000 issues), or the count can't complete, total is left out and warnings includes an include_total entry; narrow the query or add filters to get a total. get_issue_messages , and get_issue with include_messages=true , list each message's attachments with an index , a file name, and a download URL. Images aren't downloaded by default; set include_images to true when your AI tool needs to look at them. Images hosted in Pylon (PNG, JPEG, GIF, and WebP) are returned as image content, up to 5 images per call, 5 MB each and 10 MB in total, and images that can't be attached are noted in the response. To read a single attachment, call get_message_attachment with the issue , message_id , and attachment_index from a message read. Images come back as image content with the same limits. For UTF-8 text attachments hosted by Pylon, get_message_attachment returns the text in a content block and reports the read status in read . Supported extensions are CSV, TSV, JSON, JSONL, NDJSON, TXT, LOG, MD, YAML, YML, XML, SQL, INI, CONF, and TOML. Files can be up to 5 MiB, with up to 64 KiB of text per response. complete : no more text remains. partial : pass read.next_cursor as cursor with the same issue , message_id , and attachment_index to read the next page. Access is checked on every call. If the file changes, restart without a cursor. unsupported : use the download link for other formats, external files, non-UTF-8 content, or oversized files. unavailable : the download failed. Retry or use the download link. Tools that act on a single issue accept its ID or its number, as a string or an integer, and a leading # is fine. Common alternative argument names such as issue_id , issue_number , or ticket_id also work; if you send more than one and they point to different issues, the call fails before anything changes. update_issue can also set customer_portal_title , the title customers see in the customer portal, and customer_portal_visible , which shows or hides the issue in the customer portal. Omit either to leave it unchanged. search_issues results include customer_portal_title , and get_issue returns customer_portal_visible . update_issue can move an issue to another account with account_id and set its requester with requester_id , in the same call if needed. The account changes first, and the requester must be a contact in the issue's account after that change. If the issue has no account, setting requester_id also moves it to the contact's primary account. If the issue's current requester isn't in the new account, the account move fails unless you also pass requester_id with a contact in that account. Partner issues are the exception: the move keeps their partner-side requester. Neither field can be set to an empty value, so update_issue can't remove an issue's account or clear its requester. update_issues changes only the fields you provide. Issues that don't exist or that you can't update are listed in skipped_issues instead of failing the call. Tags replace the issue's tags by default; set tags_apply_mode to append_only to add tags or remove_only to remove them. Use update_issue for per-issue changes such as priority or custom fields. update_issue and update_account accept the same tags_apply_mode for tags : replace (the default), append_only , or remove_only . Adding or removing leaves other tags in place and is safe to retry. Setting tags_apply_mode requires a tag list, and omitting tags leaves tags unchanged. Saving and deleting a tag requires permission to edit issue tags, account tags, or the knowledge base, depending on the tag's object_type ( issue , account , or article ). For save_tag , omit tag_id to create a tag with object_type and value , and optionally a color . Tag values are unique per object type and compared case-insensitively, so check list_tags first and reuse an existing tag. To rename or recolor a tag, supply its tag_id , its object_type , and the value or color to change. Renaming a tag changes it everywhere it's applied. To add or remove tags on a single issue, account, or knowledge base article, use update_issue , update_account , or update_article_settings instead. delete_tag permanently deletes a tag and removes it from every issue, account, or article it's applied to. It can't be undone. If a trigger, view, dashboard, macro, or other configuration still uses the tag, the deletion is refused and the error lists what uses it. REST API AI tools can run operations from the Pylon REST API directly. Each REST API operation has its own tool: either a dedicated tool such as update_account , or a tool named after the operation, such as create_ticket_form . A tool named after an operation takes the operation's path, query, and body parameters in arguments . Each call runs as the authenticated user, so the operation's own permission checks apply, just as they do in the Pylon dashboard. If no tool does what you need, use the Pylon CLI instead. search_api_operations , get_api_operation , call_api_read , and call_api_write no longer appear in tool lists, but integrations that already call them by name keep working. Writes apply immediately and can be visible to customers. Some updates replace a whole list, such as an account's tags, so read the current value first and send the full list. Writes have no idempotency key: if a write's outcome is unknown, read the record before retrying. Pass select , a JMESPath expression, to return only the fields you need, such as data[].{id: id, name: name} . Read responses over 200 KB return an error; narrow them with select or request fewer results. If a write's response is over 200 KB, the write still succeeds and returns a short note instead of the response, so don't retry it. Each operation uses its REST API rate limit . When an operation is throttled, the error says how many seconds to wait. Some REST API operations aren't available through MCP, so they have no tool. Some operations are available only through MCP: api.usepylon.com rejects them, they aren't in the API reference , and the Pylon CLI and SDKs don't support them.
